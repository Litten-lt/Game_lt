# 横版闯关游戏项目规划 v0.1

更新日期：2026-08-07

## 1. 项目愿景

制作一款体量可控、操作流畅、关卡反馈清晰的 2D 横版闯关游戏。开发初期聚焦“移动本身是否有趣”和“玩家能否从关卡中学习并熟练运用能力”，剧情、美术规模和内容数量均服务于核心玩法，不反客为主。

## 2. 第一阶段产品边界

第一阶段交付物是一个 10～15 分钟的垂直切片，而不是完整商业版本。

垂直切片应包含：

- 标题页、开始游戏、暂停、失败重试和通关流程
- 玩家移动、跳跃、下落、受击、死亡和重生
- 一项能影响移动或战斗的核心能力
- 2～3 类敌人或机关
- 检查点和一个完整关卡
- 基础 HUD、镜头、音效、背景音乐和手柄支持
- 可导出的 Windows 测试版本

暂不纳入首个切片：

- 多人联机
- 开放世界或复杂分支地图
- 大量装备、技能树和随机词条
- 完整配音与大规模剧情演出
- 移动端适配

## 3. 待确认的产品决策

以下内容会显著影响开发，应在进入正式制作前确定：

1. 游戏基调：轻松冒险、黑暗幻想、科幻或其他方向。
2. 核心差异点：战斗、跑酷、解谜、能力组合或叙事中的哪一项最重要。
3. 目标平台：首发暂建议 Windows，后续再评估 Web 或主机。
4. 视觉方向：像素、手绘、矢量或低分辨率骨骼动画。
5. 技术引擎：建议在 Godot 与 Unity 中二选一并做小型验证。
6. 输入方案：键鼠和手柄是否同时作为首发硬性要求。

具体结论记录在 `docs/DECISIONS.md`，避免关键选择只存在于聊天中。

## 4. 核心玩法框架

### 玩家循环

观察环境 → 尝试移动或战斗 → 获得即时反馈 → 掌握规律 → 通过挑战 → 抵达检查点。

### 手感目标

- 输入响应及时，跳跃高度和距离可预测。
- 允许适量“土狼时间”和跳跃输入缓存，降低无意义失误。
- 镜头不抢夺控制感，并提前展示前进方向的危险。
- 受击、命中、落地和死亡均有明确的视觉与声音反馈。
- 检查点间距控制失败成本，重试等待尽可能短。

### 最小系统集合

- 玩家状态机
- 输入映射
- 角色运动与碰撞
- 生命、伤害和无敌帧
- 敌人基础 AI
- 关卡触发器、机关和检查点
- 镜头系统
- UI 与游戏状态切换
- 存档或最小进度记录
- 音频管理

## 5. 开发里程碑

### M0：方向确认与工程基线

完成条件：

- 确认一句话卖点、目标玩家、视觉方向和引擎
- 建立基础工程、目录规范、输入映射和导出流程
- 约定素材尺寸、单位比例、碰撞层和命名规范
- 每次合并后能够生成可运行版本

### M1：灰盒移动原型

完成条件：

- 玩家可以跑、跳、下落、穿越单向平台并正常碰撞
- 支持土狼时间、跳跃缓存和可调跳跃高度
- 完成镜头跟随、死亡区域与即时重生
- 使用灰盒完成 2～3 分钟移动测试房
- 通过试玩数据确定运动参数，而非继续凭感觉堆功能

### M2：核心能力与挑战原型

完成条件：

- 实现一项核心能力，例如近战、冲刺、钩索或环境互动
- 加入至少两类敌人或机关
- 具备伤害、击退、无敌帧和命中反馈
- 建立可复用的挑战组件，而不是把逻辑写死在单个关卡

### M3：垂直切片关卡

完成条件：

- 关卡有引导、练习、组合考验、高潮与收尾
- 10～15 分钟内展示核心能力的多种用途
- 完成检查点、失败重试、通关和基础 UI
- 替换关键占位素材，加入第一版音效与音乐
- 至少完成一轮外部试玩和问题优先级整理

### M4：打磨与可发布试玩版

完成条件：

- 修复阻断流程和高频体验问题
- 优化性能、加载时间、输入设置和基础无障碍选项
- 完成 Windows 构建、版本号、更新日志和试玩说明
- 建立后续内容扩展的估算，而不是立即承诺完整规模

## 6. 关卡设计原则

- 每个新机制遵循“安全展示 → 单独练习 → 与旧机制组合 → 最终考验”。
- 玩家失误后应能理解原因，避免不可预判的屏外伤害。
- 路线、光照、色彩和镜头共同引导，而不依赖大量文字。
- 收集物优先用于鼓励探索或教授技巧，不作为无意义填充。
- 难度来自理解与执行的递进，不来自冗长重跑和随机惩罚。

## 7. 技术与目录建议

引擎确定后再落地最终结构，建议职责大致分为：

```text
assets/       美术、动画、音频和字体源文件
docs/         策划、技术决策、测试记录
game/         可运行游戏工程
tools/        内容制作、校验和构建辅助工具
builds/       本地构建产物（不提交大型二进制）
```

技术原则：

- 运动、战斗和镜头参数尽量数据化，便于快速调试。
- 场景和脚本保持单一职责，优先组合而非深层继承。
- 对存档结构设置版本号，避免后期内容变更导致旧存档崩溃。
- 大型二进制素材进入仓库前先确认是否需要 Git LFS。
- 第三方素材和插件必须记录来源与许可证。

## 8. 测试与验收

每个里程碑都产出可试玩构建，并收集：

- 玩家完成时间、死亡点和卡住位置
- 首次理解机制所需尝试次数
- 输入延迟、碰撞异常和镜头不适
- 玩家能否说清核心能力及失败原因

问题优先级：

- P0：无法启动、无法通关、存档损坏
- P1：频繁误判、严重手感问题、核心流程故障
- P2：局部体验、表现或平衡问题
- P3：锦上添花的功能与表现优化

## 9. 风险控制

- 范围膨胀：任何新系统都说明它如何增强核心循环，否则进入候选清单。
- 美术成本：先用占位资产验证尺寸、动画数量和制作管线。
- 手感返工：最早制作测试房，将关键参数集中配置。
- 内容效率：关卡机关组件化，并在垂直切片阶段验证复用能力。
- 单人开发瓶颈：优先完成端到端小闭环，再横向扩充内容。
- 版权风险：素材、字体、音乐和插件均保留许可证记录。

## 10. 下一步工作

1. 用一句话明确游戏卖点和玩家体验。
2. 确认引擎、视觉风格、分辨率与目标平台。
3. 选择首个核心能力，并定义玩家的完整动作列表。
4. 搭建最小工程和灰盒测试房。
5. 用第一轮试玩结果调整 M1，而不是直接进入内容量产。
